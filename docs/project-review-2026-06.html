1.요약 (Executive Summary)

전체 평가와 핵심 결론을 한 페이지로 정리합니다.

B종합 등급

“설계 철학은 A급, 프론트엔드 구조와 도구 체계가 따라오지 못한 상태.”

데이터 정직성(누락 필드 추적, 출처 표기, 가짜 데이터 금지 게이트)과 순수 함수 기반 스코어링 라이브러리는 개인 프로젝트 수준을 넘는 완성도입니다. 반면 UI 전체가 단일 1,272줄 파일에 들어 있고, 린트/타입 체계가 없으며, 실사용자에게 보이는 버그(날짜 표기, CSV 한글 깨짐, 매 방문 전체 데이터 재다운로드)가 몇 건 확인되었습니다.

  • 구조: 리팩토링의 최우선 대상은 src/App.jsx(1,272줄)와 src/styles.css(2,238줄)의 분해입니다. 도메인 로직(src/lib)은 이미 잘 분리되어 있어 손댈 필요가 거의 없습니다.
  • 데이터: 한국 ETF 1,133개(84%)가 3·5년 수익률과 리스크 지표가 전부 비어 있어 AIYN 점수의 시장 간 비교성이 깨져 있습니다. Yahoo .KS 심볼로 보강하는 것이 가장 투자 대비 효과가 큰 단일 개선입니다.
  • 도구: ESLint/Prettier/TypeScript(또는 JSDoc) 부재가 향후 회귀 버그의 주요 위험원입니다. 이번에 확인된 날짜 포맷 버그도 린트가 있었다면 잡혔을 유형(이중 이스케이프된 정규식)입니다.
  • 방향: 백엔드 없는 정적 구조는 이 제품의 강점이므로 유지를 권장합니다. 차별화 포인트는 “데이터 정직성”이며, 이를 UI 전면(점수 신뢰도 배지)으로 끌어올리는 것이 제품 전략의 핵심입니다.

2.프로젝트 구조 분석

아키텍처, 데이터 흐름, 모듈 구성을 정리합니다.

2.1 아키텍처 개요

EIAYN은 “빌드 타임 데이터 스냅샷 + 정적 SPA” 아키텍처입니다. 브라우저는 외부 금융 API를 직접 호출하지 않고, GitHub Actions가 빌드 시점에 공개 데이터를 수집해 public/data/etfs.json으로 굽고, React 앱은 이 파일 하나만 읽습니다. 서버·DB·API 키가 전혀 없어 운영 비용이 0원이며, 평일 아침 스케줄(cron 30 21 * * 0-5)로 자동 갱신됩니다.

그림 1. 빌드 타임 데이터 파이프라인과 정적 SPA의 분리 구조. src/lib는 파이프라인과 UI가 공유합니다.

구조적으로 잘 한 점 스코어링·지표 계산을 src/lib 순수 함수로 분리해 Node 파이프라인과 브라우저가 같은 코드를 쓰고, 같은 단위 테스트로 검증됩니다. “점수가 UI에 하드코딩되지 않고 스냅샷에서 결정된다”는 원칙이 check-data.mjs의 금지어 검사(demo/mock/예시)로 강제됩니다.

2.3 상태·URL 관리 방식

라우팅 라이브러리 없이 URLSearchParams를 직접 읽고(deepLink.js), history.replaceState로만 URL을 갱신합니다. 딥링크(?code=QQQ) 진입은 잘 동작하지만 pushState가 한 번도 없어 브라우저 뒤로가기로 화면 전환을 되돌릴 수 없고, URL 동기화 시점도 화면마다 제각각입니다(분석 진입 시엔 갱신, 비교 추가 시엔 미갱신). 4절 P1-4에서 다룹니다.

강점 (유지·강화할 것)

  • null 규율: 누락 데이터를 0으로 조작하지 않고 null로 보존, missingFields로 추적. 점수 계산은 누락 팩터를 제외하고 가중치를 재배분 (scoring.js:17-21).
  • 아웃라이어 내성: 수익률 팩터는 백분위 정규화를 사용해 레버리지 ETF 1~2개가 전체 분포를 압축하지 못함 — 테스트로 검증됨 (scoring.test.js:72-87).
  • 출처 투명성: ETF마다 필드 단위 출처(dataQuality.sources)를 기록. 금융 정보 도구로서 드문 수준의 정직성.
  • 배포 게이트: check-data.mjs가 시장별 최소 개수·필수 필드·금지어를 검증해 불량 스냅샷 배포를 차단.
  • 견고한 수집 계층: 재시도+백오프, 타임아웃, 동시성 제한(mapLimit), 필수/선택 소스 구분 (http.mjs).
  • 접근성 기본기: aria-label, role=tablist, 시맨틱 태그, 보조 클릭(Cmd/Ctrl+클릭) 허용 링크 처리 (App.jsx:1048-1061).
  • 문서: 데이터 소스의 한계까지 명시한 DATA_SOURCES.md, 산식을 공개한 docs/scoring.md.

약점 (리팩토링 대상)

  • UI 모놀리스: 19개 컴포넌트가 App.jsx 한 파일. 컴포넌트 단위 테스트·재사용·리뷰가 모두 어려움.
  • CSS 모놀리스: 302개 클래스가 전역 1파일. 죽은 스타일 식별 불가, 이름 충돌 위험.
  • 도구 부재: ESLint·Prettier·타입 체계·lint CI가 전혀 없음. 이번에 발견된 정규식 버그(아래 P1-1)는 린터(no-useless-escape)가 잡는 유형.
  • 중복 유틸: nullableNumber 3곳, emptyProfile 4곳, zeroDecimalCurrency 2곳에 복제됨.
  • 죽은 코드/의존성: normalizeEtfInput은 테스트에서만 사용, parsePercent는 단순 별칭, playwright는 설치만 되고 미사용.
  • placeholder UI: 비활성 버튼 8곳(다크모드·알림·도움말·편집·더보기·패널 접기 등), / 단축키 힌트는 표시만 되고 핸들러 없음.
  • 테스트 공백: React 컴포넌트 0%, 스크래핑 파서(HTML 구조 변경에 가장 취약한 부분) 픽스처 테스트 0%, E2E 0%.
  • 에러 격리 없음: ErrorBoundary 부재 — 단일 렌더 예외로 전체 화면이 백지화될 수 있음.

P1 — 동작 결함 (즉시 수정 권장, 합계 반나절 분량)

#문제위치상세 및 수정 방안
P1-1 날짜가 “2026 06. 05. 11:32”로 표시 src/lib/format.js:55 .replace(/\\. /g, '-')의 정규식이 이중 이스케이프되어 리터럴 백슬래시를 찾고 있어 치환이 전혀 일어나지 않습니다. 실제 출력을 재현해 확인했습니다(의도: 2026-06-05 11:32). /\. /g로 수정하면 됩니다. 푸터·사이드바·시세 기준 표기 전부에 보이는 버그입니다.
P1-2 CSV 내보내기 한글 깨짐 src/App.jsx:217-222 UTF-8 BOM 없이 저장되어 Excel(Windows)에서 ETF명·시장 컬럼의 한글이 깨집니다. '﻿' + csv 한 줄로 해결됩니다.
P1-3 매 방문 6.7MB 전체 재다운로드 src/hooks/useEtfData.js:14 cache: 'no-store'가 조건부 요청(ETag/304)까지 차단해 데이터가 그대로여도 매번 풀 다운로드(gzip 0.64MB)가 발생합니다. 'no-cache'(재검증 허용)로 바꾸거나, 빌드 시 파일명에 콘텐츠 해시를 붙이고 장기 캐시하는 방식을 권장합니다.
P1-4 브라우저 뒤로가기 미동작 src/App.jsx:1258-1270 화면 전환(비교↔분석, ETF 변경) 시 replaceState만 사용해 히스토리가 쌓이지 않습니다. 분석 화면에서 뒤로가기를 누르면 사이트 이탈됩니다. pushState + popstate 리스너(또는 경량 라우터)로 전환해야 합니다.
P1-5 CSV 수식 인젝션 미방어 src/App.jsx:1221-1225 외부에서 스크랩된 문자열(ETF명·티커)이 =, +, -, @로 시작하면 Excel에서 수식으로 실행될 수 있습니다. csvCell에서 해당 접두 문자를 '로 이스케이프해야 합니다.

P2 — 구조·유지보수 부채

#문제위치상세
P2-1 App.jsx 모놀리스 src/App.jsx (1,272줄) App, Sidebar, TopBar, WorkspaceHeader, ComparisonGrid, EtfAnalysisDashboard, AnalysisPanel, RankingPanel, Radar, Sparkline 등 19개 컴포넌트 + CSV/차트 헬퍼 12개가 한 파일. 변경 충돌·리뷰 비용이 크고 컴포넌트 테스트가 사실상 불가능합니다. 6절 Phase 1에서 분해안을 제시합니다.
P2-2 AIYN 점수의 시장 간 비교성 깨짐 scoring.js + UI 전반 한국 ETF 1,133개는 3년 리스크 지표가 전부 null이어서 점수 커버리지가 0.68(가중치 68%만 반영)인 반면 미국 핵심 ETF는 0.90입니다. 즉 한국 ETF 점수에는 ‘안정성’ 팩터가 빠져 있는데, UI는 scoreCoverage를 전혀 표시하지 않아 동일 잣대 점수처럼 보입니다. 비교 화면에서 한·미 ETF를 나란히 두는 핵심 시나리오에서 오해를 유발합니다. → 데이터 보강(5절) + 신뢰도 배지(7절 F-3).
P2-3 페이로드의 30%가 중복 메타데이터 public/data/etfs.json 6.7MB 중 dataQuality(주로 ETF마다 반복되는 출처 객체)가 1.97MB를 차지합니다. 출처를 최상위 사전으로 정규화하고 ETF에는 인덱스만 두면 원본 기준 약 25~30% 감량이 가능합니다. 추가로 상세 필드(보유종목 0.7MB, 스파크라인 0.15MB)를 코어/디테일 파일로 분리하면 첫 화면 로딩이 더 가벼워집니다.
P2-4 override가 사실상 fallback scripts/fetch-etf-data.mjs:326-331 mergeProfiles는 먼저 온 값이 이기는 구조인데 profileOverrideForTicker가 배열의 마지막에 있어, 스크랩 소스가 잘못된 값을 주면 수동 보정값이 적용되지 않습니다. 이름(override)과 동작(fallback)이 어긋나 있어 우선순위를 명시적으로 분리해야 합니다.
P2-5 빌드가 외부 네트워크에 결합 package.json build 스크립트 npm run build가 항상 data:update(외부 API 수십~수천 호출)를 실행합니다. 코드만 고친 배포도 K-ETF/Yahoo 장애 시 실패하고, 로컬 빌드도 네트워크 필수입니다. 데이터 갱신 워크플로(스냅샷 커밋/아티팩트)와 사이트 빌드를 분리하는 것을 권장합니다.
P2-6 검색이 키 입력마다 전체 재연산 src/lib/search.js:13-29 searchableText가 키 입력마다 1,348개 ETF × (이름+보유종목 연결 문자열)을 새로 만듭니다. 현재는 체감 가능한 경계 수준이지만, 유니버스 확대 시 바로 병목이 됩니다. 데이터 로딩 시 1회 사전 계산(인덱스) + 입력 디바운스로 해결됩니다.
P2-7 중복 유틸·죽은 코드 여러 파일 nullableNumber(fetch-etf-data·normalize·k-etf), emptyProfile(4곳), zeroDecimalCurrency(format·fetch-etf-data) 중복. normalizeEtfInput은 앱에서 미사용, parsePercent는 toFiniteNumber의 별칭, playwright는 미사용 devDependency.

P2-9 스크래핑 파서 무테스트 scripts/data/stockanalysis.mjs 등 HTML 테이블 구조에 의존하는 파서(가장 깨지기 쉬운 코드)에 고정 픽스처 테스트가 없습니다. 소스 구조가 바뀌면 “조용히 null”이 되어 check:data의 필수 필드 검사에 걸리기 전까지 모릅니다.

8.향후 방향 제언

기술 선택을 넘어, 이 제품이 무엇으로 차별화될지에 대한 제언입니다.

① 정적 아키텍처를 유지하라 — 백엔드는 ‘필요해질 때’가 아니라 ‘피할 수 없을 때’

운영비 0원, 장애 지점 없음, 키 관리 없음은 개인이 지속 가능하게 운영할 수 있는 결정적 조건입니다. 검토한 기능 제언(F-1~F-15) 전부가 정적 구조 안에서 구현 가능합니다. 계정·실시간 알림·커뮤니티가 정말 필요해지는 시점까지 백엔드 도입을 미루고, 그때도 서버리스 함수 1~2개 수준에서 시작하길 권합니다.

② 차별화 축은 “데이터 정직성” — 이미 가진 강점을 전면에

누락 필드 추적, 필드 단위 출처 표기, 가짜 데이터 금지 게이트는 이 프로젝트가 이미 갖춘, 흔치 않은 자산입니다. 그러나 현재 UI에서는 이 정직성이 거의 보이지 않습니다. 점수 신뢰도 배지(F-3), 출처 툴팁, “이 값은 어디서 왔나” 패널로 신뢰성을 사용자 경험으로 끌어올리면 “출처가 투명한 ETF 스크리너”라는 명확한 포지셔닝이 됩니다.

③ 가장 가치 있는 단일 투자: 한국 ETF 장기 데이터 보강

유니버스의 84%인 국내 ETF가 장기 수익률·리스크 지표 없이 평가되고 있다는 것이 현재 제품의 가장 큰 약점입니다. Yahoo .KS 보강(Phase 2)은 기존 파이프라인 재사용으로 비용이 작은 반면, 점수 비교성·랭킹 품질·F-6/F-10 같은 후속 기능의 토대가 되는 가장 레버리지 높은 작업입니다.

④ 의존 리스크는 “감지”로 관리

Yahoo 비공식 엔드포인트와 StockAnalysis 스크래핑은 언제든 깨질 수 있는 외부 의존입니다. 이를 없앨 수는 없으므로 (무료 공개 소스의 본질), 파서 픽스처 테스트(Phase 3)와 수집 실패 시 “이전 스냅샷 유지 + 경고” 전략(Phase 2의 워크플로 분리로 자연 확보)으로 깨짐을 빨리 알고 우아하게 버티는 체계를 갖추는 것이 현실적인 답입니다.

⑤ 권장 실행 순서 요약

지금 Phase 0 버그 수정 → 2주 내 Phase 1 구조 정비 + F-3·F-7 같은 저비용 기능 → 1~2개월 Phase 2 데이터 보강·성능 + F-2·F-6 → 분기 단위 Phase 3 타입·테스트와 장기 기능(F-9, F-12).
